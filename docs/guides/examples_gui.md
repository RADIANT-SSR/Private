# GUI Worked Examples

Six short walkthroughs, each a task rather than a tour: build a sensor from nothing,
read a validated flagship baseline metric group by metric group, adopt a detector
from the part library, edit an optical train, sweep a parameter, and compare nine
configurations at once. Each one is a few minutes of clicking and ends with numbers
you can check against this page.

Every figure in this chapter is a capture of the real application, generated by
`scripts/gen_gui_screenshots.py` driving `RADIANTMainWindow` offscreen on a committed
config. Regenerate the whole set with one command:

```bash
python scripts/gen_gui_screenshots.py --all
```

The offscreen renderer paints platform-neutral chrome, so the figures look the same
whoever produced them and on whichever operating system. Your own window will carry
your platform's title bar and, if you have chosen the dark theme, your own colours;
nothing else differs.

**A convention used throughout.** The window has three permanent columns: the
**Parameters** dock on the left (the full schema, as a tree, with a provenance badge
on every value), the **stage workspace** in the middle (whichever of the ten chain
stages is selected in the strip along the top), and the **right rail** (pinned metric
cards, the `Edit Config (YAML)` button, and the Messages panel). Stages whose content
does not fit one pane are tabbed — Geometry is *Inputs | Schematic*, Optics is
*Inputs | Transmission | MTF | PSF + Pupil*, Detector is *Inputs | Noise | Detector +
PSF*. Walkthroughs below name the tab whenever it matters.

## Walkthrough 1 — Build a sensor from scratch

**Goal:** go from an empty window to a first evaluated result, understanding at each
step which stage you are describing.

The chain runs geometry first (where is the sensor, where is the target, how far
apart), then source, atmosphere, optics, platform, spectral integration, detector,
readout, calibration, and finally performance. Filling the stages in strip order is
therefore also filling them in the order the physics consumes them.

1. **Start empty.** `radiant gui` with no path, or `File → New`. The window opens on
   the welcome screen — "Start a scenario" — whose first tile is **Blank config**
   ("Start from schema defaults and set everything yourself"). Take it and you land
   in the Geometry workspace with every parameter at its schema default.

2. **Place the sensor and the target.** Select stage **1 Geometry**, tab **Inputs**.
   The centre pane leads with a derived scene-class label — `Scene: air → ground
   (air_to_ground) — derived` — and then offers one card per geometry *family*, each
   asking you to pick one mode. Set `sensor_altitude_m` to 8000 m and leave
   `target_altitude_m` at 0 m and `path_zenith_rad` at 0 deg; that is a nadir view
   from 8 km.

   ![Geometry workspace, Inputs tab. The Parameters dock is widened so the full
   dot-path of every parameter is legible.](figures/gui/build_geometry_inputs.png)

   Note the third column of the Parameters dock. `sensor_altitude_m` reads `config`
   because you set it; everything else reads `default`. That badge is how you tell
   what you have actually specified from what the schema supplied — and it is the
   same distinction the YAML round-trip preserves.

   The greyed fields are not disabled features. Geometry accepts one mode per
   family, and the fields of the modes you did not pick are shown inert rather than
   hidden, so the alternatives stay visible. Here `path_zenith_rad` is the chosen
   viewing mode, so `sensor_off_boresight_rad`, `ground_range_m`,
   `elevation_angle_rad`, and `target_range_m` are all derived rather than entered.

3. **Check the geometry you just described, not the numbers you typed.** Switch to
   the **Schematic** tab.

   ![Geometry workspace, Schematic tab — the 2D viewing-triangle schematic with the
   sensor, target, sun vector, and the labelled angle set.](figures/gui/build_geometry_schematic.png)

   The schematic is deliberately **not to scale**: an 8 km altitude drawn to scale
   against a 6371 km Earth radius would be invisible. Altitudes are carried by leader
   labels (`h_s 8.0 km`) while the geometry itself stays legible. The sun vector
   (orange) and the sensor line of sight (blue) are drawn from the solar geometry you
   set — here a 28.65 deg solar zenith at day-of-year 80, local solar time 12 h.

4. **Give it a telescope.** Select stage **4 Optics**, tab **Inputs**.

   ![Optics workspace, Inputs tab — aperture and wavefront-error entry on the left,
   the derived optics outputs beneath.](figures/gui/build_optics_inputs.png)

   Set `aperture_diameter_m` to 0.3 m and `focal_length_m` to 1.2 m. The f-number
   field immediately reads 4 and carries a lightning bolt with a `derived` badge —
   it is computed, not stored, and typing into it is not how you change it. Beneath
   the form, the Outputs readout shows what the stage handed downstream: collecting
   area 0.0706858 m², pixel solid angle 2.25 × 10⁻¹⁰ sr, cone solid angle 0.0485195
   sr, and — the important one — `Regime: extended`.

   That last line is the radiometric regime, classified here in the optics stage and
   never re-decided later. No target extent was specified, so the 300 K scene fills
   the pixel footprint: the target signal is a radiance integrated over the pixel
   solid angle, and the ensquared-energy fraction is reported as a spatial metric
   rather than applied to the signal.

5. **Evaluate.** Press `Evaluate` (F5), or simply keep editing — the window
   re-evaluates on a debounce after every committed change. The status bar reports
   `Evaluated — 500 wavelength points`.

6. **Read the result.** Select stage **10 Performance**.

   ![Performance workspace on the minimal MWIR example after
   evaluation.](figures/gui/performance_workspace.png)

   For this configuration the headline numbers are SNR 1124, NEDT 24.96 mK, GSD
   0.12 m, and system MTF at Nyquist 0.2668. The pinned cards in the right rail carry
   the same four plus NIIRS, which reads `n/a — not computed for this run`: the
   GIQE-5 regression is out of range for a 0.12 m GSD thermal scene, and the tool
   says so rather than extrapolating quietly.

7. **Save it.** `File → Save As…` writes exactly what you specified — the `config`
   rows, not the defaults — so the file stays readable and the schema stays free to
   move underneath it.

## Walkthrough 2 — Open a flagship baseline and read every metric group

**Goal:** understand what each metric group is telling you, on a configuration whose
answers are already known.

We use `scenarios/09_flagship_missions/9.2_landsat_tirs_nedt/tirs_b10_nedt_300k.yaml`:
Landsat 9 TIRS band 10, a 705 km sun-synchronous f/1.64 refractive LWIR pushbroom on
a 25 µm QWIP focal plane, viewing a 300 K unit-emissivity blackbody through a vacuum
path — the same view the published on-orbit NEdT is measured against.

1. **Open it.** `File → Open YAML…`, or `radiant gui
   scenarios/09_flagship_missions/9.2_landsat_tirs_nedt/tirs_b10_nedt_300k.yaml`. The
   window evaluates on load.

2. **Go to Performance.**

   ![Performance workspace on the TIRS band-10 baseline. All five metric groups are
   enabled and populated.](figures/gui/flagship_performance.png)

3. **Read the groups in order.** The `Compute:` row of checkboxes above the cards is
   the metric-group selector; each ticked group is a family of metrics the chain was
   asked to produce. Untick one and its inputs stop being computed, which is how you
   buy back time on an expensive configuration.

   - **Sampling / geometry** — GSD 99.02 m in both axes (against the published 100 m
     thermal product), ground range 0 m (nadir), $Q$ = 0.7153 at band centre, and
     the resulting classification `detector-limited`. $Q = \lambda F/\# / p$ compares
     the optical blur to the pixel: below 1 the optics pass more detail than the
     25 µm pixels can sample. The diffraction limit is 122.6 µrad, which projects to
     86.41 m at the target — smaller than the 99.02 m sample, which is the same
     statement again.
   - **Spatial / MTF** — FWHM 26.28 µm in both axes, RER 0.6791, ensquared energy
     0.508 in the central pixel and 0.9081 over 3×3, MTF at Nyquist 0.3533, folded
     MTF 0.7066, alias fraction 0.5. The folded value is exactly twice the unfolded
     one and the alias fraction is exactly 0.5: at Nyquist the first sampling replica
     lands back on Nyquist, so half the apparent contrast there is folded-in
     above-Nyquist scene content. Strehl reads 1 because this config carries no
     wavefront error.
   - **Radiometric** — SNR 1160, contrast SNR 1160, SCNR 1160, NEDT 58.07 mK. The
     three SNR flavours coincide because the scene is a uniform blackbody: there is
     no separate clutter or contrast term to divide them.
   - **Interpretability** — MRT at Nyquist 0.3698 K, and NIIRS reported as
     `yes — outside GIQE-5`. The MRT is the NEDT divided by the system MTF at that
     frequency; it is the temperature difference a human observer needs to resolve a
     bar pattern at the sampling limit.
   - **Saturation** — well margin 9.791 dB, ADC margin 9.789 dB, dynamic range
     71.08 dB. Margins are the headroom between the filled well and its capacity;
     they go to 0 dB exactly when the pixel clips.

   The result to check: RADIANT predicts NEdT = 58.07 mK where the flight-measured
   value is 49 mK and the requirement is ≤ 400 mK. The prediction sits inside the
   58–124 mK bracket the scenario derives from the two published conversion-efficiency
   bounds, and it clears the spec by almost an order of magnitude.

4. **Ask where the spatial number came from.** Select stage **4 Optics**, tab **MTF**.

   ![Optics workspace, MTF tab — the system MTF with its contributor terms, and the
   per-term budget table beneath.](figures/gui/flagship_mtf_budget.png)

   The system curve (black) is the product of every contributor. Only two contributors
   bite here: the optics term (blue, from the autocorrelation of the complex pupil)
   and the pixel-aperture term (gold, the sinc of the 25 µm detector footprint). The
   table below reads them at fractions of Nyquist — at 1 × Nyquist,
   `mtf_optics` = 0.5549 against `mtf_pixel_aperture` = 0.6366, while charge diffusion,
   electronics, IPC, jitter, smear, and TDI all sit at 1 and are noted as
   "≈ 1.0 across band (not drawn)". The dashed vertical marks Nyquist at 3.56
   cycles/mrad. The pixel term's first zero is out past 7 cycles/mrad and it rings
   afterwards — that gold lobe beyond 10 cycles/mrad is the sinc sidelobe, above
   Nyquist and therefore aliased rather than resolved.

5. **Ask where the radiometric number came from.** Select stage **7 Detector**, tab
   **Noise**.

   ![Detector workspace, Noise tab — the per-term noise budget on a log axis beside
   the same terms as a table.](figures/gui/flagship_noise_budget.png)

   Sixteen noise terms are always computed; four are non-zero here. Signal shot
   dominates at 1273 e- RMS, then dark shot at 373.6 e- RMS, quantization at
   352.4 e- RMS, and read noise at 260 e- RMS. The terms combine in quadrature to a
   total of 1397 e- RMS, and the caption lists the twelve terms below 0.05 e- RMS
   that were computed and not drawn. This is a shot-noise-limited detector, which is
   what "photon-limited" means in practice: the 260 e- RMS read noise, large as it is
   in absolute terms, contributes under 4 % of the total in quadrature.

## Walkthrough 3 — Pick an FPA from the part library

**Goal:** stop typing detector parameters one at a time and adopt a real part, with
its provenance attached.

RADIANT ships a library of focal-plane presets — real parts, each traced to a
datasheet line in a manifest. Applying one writes a *set* of detector parameters at
once and marks each of them as preset-supplied, so a later reader can tell which
numbers came from the part and which you chose yourself.

1. **Select stage 7 Detector, tab Inputs.** The top strip of the pane is the FPA part
   library row. On a config with no part applied it offers `Choose part & apply…`
   alone.

2. **Choose a part.** `Choose part & apply…` opens the **FPA part library** table —
   one row per preset, with columns *Part*, *Kind*, *Class*, *Band*, and *Values
   (basis census)*, plus a details pane for the selected row. Select a part and
   confirm to apply it.

   The picker is a modal dialog, and the figure set for this manual is captured
   offscreen where modal dialogs cannot be photographed cleanly; the figure below
   therefore shows the state you are left in *after* applying, which is the state
   that matters.

3. **Read what the preset did.**

   ![Detector workspace, Inputs tab, on a config built from the GeoSnap-18 preset.
   The library row reports the part and how many parameters it supplied; the
   Parameters dock badges each of them `preset`.](figures/gui/fpa_preset_detector.png)

   The library row now reads `FPA part library  geosnap-18: 12 applied`, with
   `Details…` and `Remove` beside it. In the Parameters dock the twelve
   preset-supplied values carry a `preset` badge instead of `default` or `config`:
   `pixel_pitch_x_um` = 18 µm, `pixel_pitch_y_um` = 18 µm, `fill_factor` = 1,
   `qe_value` = 0.85, `detector_temperature_K` = 110 K, and the rest. Every one of
   them traces `fpa:geosnap-18/<source>` in the run's provenance record.

4. **Override what the part does not know.** `dark_rate_e_per_s` reads
   50000 1/s with a `config` badge, not a `preset` one — it was set in the config
   *after* the preset was applied, and that is deliberate: a datasheet dark current
   is quoted at the vendor's operating point, not at yours, so the analyst owns it.
   A preset supplies a starting point; it never locks a parameter.

5. **Evaluate.** For this MWIR LEO configuration the result is SNR 1178, NEDT
   23.82 mK, GSD 0.12 m, MTF at Nyquist 0.2668.

6. **Remove it cleanly.** `Remove` lifts the preset and returns each of the twelve
   parameters to whatever it was before — it does not leave the values behind as
   orphaned `config` entries.

## Walkthrough 4 — Edit an optical element train

**Goal:** replace a single scalar throughput with a real train of coated surfaces,
and see both the transmission and the self-emission that follow from it.

A scalar `transmission_scalar` is a fine first cut. A thermal system needs more:
every warm optical surface both attenuates the scene and emits into the detector, and
the emission is set by Kirchhoff's law from the surface's own reflectance and
transmittance. RADIANT will not accept an emissivity you type in for an optical
element; it derives it.

We use `scenarios/09_flagship_missions/9.4_landsat_oli2_snr/oli2_b04_snr_ltyp.yaml`
— Landsat 9 OLI-2 band 4 (red), a config that carries the published four-mirror
silver train plus a refractive window and a per-band interference filter.

1. **Select stage 4 Optics, tab Transmission.**

   ![Optics workspace, Transmission tab — the element train as editable rows, with
   the selected element's coating curve beneath.](figures/gui/element_train_transmission.png)

2. **Read the mode switch.** The `TRANSMISSION DEFINED BY:` selector at the top has
   two positions, `Scalar throughput` and `Element train`, and here the train is
   selected. The note under it is explicit about the consequence: `Element train
   defines transmission (6 elements) — scalar τ ignored`. The scalar is still in the
   config; it is simply not in the calculation. Nothing is silently merged.

3. **Read a row.** Each row is one surface: a name, a transfer mode, a descriptive
   kind, the R or T value (a scalar, a CSV path, or an inline table), the element's
   own temperature in kelvin, and the **derived** emissivity. The four silver mirrors
   M1–M4 are `REFLECTIVE` / `mirror` at 293.0 K with ε = 0.0184 each; `fpa_window` is
   `REFRACTIVE` / `window` at 240.0 K with ε = 0.0000.

   The ε column is read-only. For a mirror it is $\varepsilon = 1 - R$; for a
   transmissive element it is $\varepsilon = 1 - T - R$. Specifying both a
   reflectance and an emissivity for the same surface over-specifies the energy
   balance, so the tool derives rather than accepts. ε = 0.0184 on these mirrors is
   $1 - R$ for $R = 0.9816$ — the value the silver coating's own curve takes where
   the derivation is evaluated.

4. **Edit it.** `Add mirror`, `Add refractive`, `Remove`, and the up/down arrows
   reorder the train; `Spectrum…` opens an inline wavelength/value table and
   `CSV file…` points a row at a measured coating curve. Every edit commits as you
   make it — there is no Apply button to forget — and each is undoable from
   `Edit → Undo`. The chain re-evaluates on the debounce, so the transmission plot
   and the downstream metrics move as you type.

5. **Inspect one coating.** Selecting a row draws its curve on its own native source
   grid beneath the table — here `Coating detail — M1 (native source grid)`, showing
   reflectance rising from about 0.94 at the short-wavelength edge to above 0.98 across
   the rest of the plotted range.
   The curve is drawn on the grid the data came in on, not on the chain's resampled
   grid, so you are checking the input rather than the interpolation.

6. **Read the effect.** Band 4 evaluates to SNR 340.6, NEDT 12.02 mK, GSD 28.65 m,
   MTF at Nyquist 0.5937. The published requirement for OLI-2 band 4 is SNR ≥ 90 at
   typical radiance and the recalled Landsat 8 flight value is about 225, so 341 is a
   consistent over-prediction of the kind this model produces where band-average QE
   and filter peak are generous and where PRNU, striping, and calibration-transfer
   noise are not modelled.

## Walkthrough 5 — Run a sweep

**Goal:** turn one evaluated point into a trade curve without writing a script.

1. **Choose the axis.** Open `examples/mwir_leo_minimal.yaml` and select stage
   **4 Optics**. The Parameters dock shows the optics branch; the parameter we are
   about to sweep, `optics.aperture_diameter_m`, currently reads 0.3 m with a
   `config` badge.

   ![The Parameters dock, optics branch. `aperture_diameter_m` is the sweep axis;
   `f_number` below it is derived and moves with
   it.](figures/gui/sweep_parameter_panel.png)

   Note `f_number` two rows down: 4, lightning bolt, `derived`. Sweeping the aperture
   at fixed focal length sweeps the f-number too. A sweep axis drags its dependants
   with it, which is usually what you want and occasionally a trap — if you meant to
   hold f/# constant you must sweep focal length alongside.

2. **Open the sweep.** `Run → Run Sweep…`. The dialog asks for a parameter, a start,
   a stop, a number of points, and a metric; a second parameter block turns the run
   into a 2-D surface. The metric list is populated from the metrics the last
   evaluation actually produced, so you cannot sweep against a metric this
   configuration does not compute.

3. **Fill it in.** Parameter `optics.aperture_diameter_m`, start 0.15 m, stop 0.60 m,
   10 points, metric `snr`. The run evaluates on a worker thread, so the window stays
   responsive and the run can be cancelled.

4. **Read the curve — and the place it stops being a curve.** The result for this
   configuration:

   | Aperture diameter [m] | SNR [-] |
   |---|---|
   | 0.150 | 561.94 |
   | 0.200 | 749.31 |
   | 0.250 | 936.67 |
   | 0.300 | 1124.03 |
   | 0.350 | 1311.38 |
   | 0.400 | 1414.17 |
   | 0.450 | 1414.17 |
   | 0.500 | 1414.17 |
   | 0.550 | 1414.17 |
   | 0.600 | 1414.17 |

   Up to 0.35 m, SNR is exactly linear in diameter: 561.94 / 0.150 = 3746 and
   1311.38 / 0.350 = 3747 per metre. That is the signature of a shot-noise-limited
   extended-source system. Collected signal goes as $D^2$, shot noise goes as
   $\sqrt{S} \propto D$, so $\mathrm{SNR} \propto D$ — not $D^2$.

   At 0.40 m the curve goes flat at 1414.17 and stays there. This is not a physical
   asymptote; it is the full well. The Messages rail fills with saturation warnings
   ("full well saturated — signal + dark + glow + near-field + stray = 2.246 × 10⁶ e-
   exceeds full_well_capacity_e = 2 × 10⁶ e-, fill fraction 1.12. Signal clipped …
   Downstream SNR/NEDT/NIIRS reflect the CLIPPED signal"). Clipped signal divided by
   clipped shot noise is $\sqrt{2 \times 10^6} = 1414.2$ — a constant, and a number
   that no longer responds to the scene at all. **The flat part of this curve is the
   tool refusing to lie, not the sensor plateauing.** The fix is a shorter
   integration time, a deeper well, or less throughput; not a bigger telescope.

5. **Keep the numbers.** The finished sweep is retained on the window;
   `File → Export Sweep CSV…` writes it out. The same run from a script is
   `sensor.sweep("optics.aperture_diameter_m", apertures, metric="snr")` — one GUI
   action, one API call, and chapter 3 runs exactly that.

## Walkthrough 6 — Compare configurations

**Goal:** hold one instrument fixed and vary only what genuinely differs between
several versions of it, then read them side by side.

RADIANT's multi-configuration model works like CODE V zoom configurations. A
parameter is **shared** — one value for every configuration — until you explicitly
configure it, at which point it carries one value per configuration, densely. A study
therefore states what differs, not what is repeated.

We use `scenarios/09_flagship_missions/9.4_landsat_oli2_snr/oli2_all_bands_study.yaml`:
all nine Landsat 9 OLI-2 bands as one study on one instrument.

1. **Open it.** `File → Open YAML…`. Because the file carries a `configurations:`
   section, the same Open action that loads a plain config loads the whole study; the
   status bar says so.

   ![Performance workspace on the nine-band OLI-2 study. The configuration selector
   runs across the top; every metric group shows one column per
   configuration.](figures/gui/compare_configurations.png)

2. **Read the selector.** The `CONFIGURATIONS` bar lists B1_CA through B9_Cirrus,
   each with a colour chip, and B4_Red is the displayed one. Selecting a different
   tab swaps which configuration the stage workspaces and the pinned cards describe;
   it does not re-run anything, because all nine were evaluated in one pass on load.
   The status bar confirms it: `B4_Red — Evaluated — 500 wavelength points (9
   configurations evaluated)`.

3. **Read the matrix.** Every metric group card grows one column per configuration,
   colour-keyed to the selector. In Sampling / geometry, GSD is 28.65 m in every
   column — pitch, focal length, and altitude are shared, so the ground sample cannot
   differ. What does differ is everything wavelength-dependent: the diffraction limit
   runs 4.003 µrad in B1 (443 nm) to 5.915 µrad in B4 (655 nm), and at the target
   2.822 m to 4.17 m. $Q$ runs 0.08076 to 0.1193 — deeply detector-limited in every
   band, as a 0.135 m aperture at 705 km must be.

   In Spatial / MTF the same wavelength dependence shows up as blur: FWHM 35.55 µm
   in B3 against 36.73 µm in B4, MTF at Nyquist 0.6073 in B1 falling to 0.5937 in B4,
   ensquared energy 0.8892 in B1 against 0.8473 in B4. One telescope, one focal
   plane, and a monotone degradation with wavelength that nobody had to enter.

4. **Check the study against flight.** The nine SNR predictions are 177, 496, 472,
   341, 238, 328, 367, 227, and 139 for B1 through B9 respectively, against
   requirements of 130, 130, 100, 90, 90, 100, 100, 80, and 50. Every band clears its
   requirement; the ratio to recalled Landsat 8 flight values sits between 0.77 and
   2.04.

5. **Edit once, move everything.** Change a shared parameter — `aperture_diameter_m`,
   say — and all nine configurations move together on the next evaluation. Change a
   configured one and only its own column moves. `Edit → Configurations…` is where a
   shared parameter becomes configured (and back); the Parameters dock marks a
   configured parameter with a badge so you can always tell which kind you are about
   to edit.

6. **Compare files instead of configurations.** When the versions you want to compare
   are separate files rather than configurations of one study — a vendor's proposal
   against your own model, say — use `Tools → Compare Config Files…` instead. It
   takes the current config plus any number of files added with `Add config file…`,
   evaluates them all on a worker thread with a progress bar, and lays the metrics out
   as one table. Use the configuration set when the instrument is one instrument; use
   the file comparison when it is genuinely several.

## Where to go next

Every walkthrough above has a scripted counterpart. The same sweep is
`Sensor.sweep`, the same comparison is `ConfigurationSet.compare`, and the same
element train is a list in the YAML. Chapter 3 runs six programs that do exactly
that, and prints what they produced.

For the full per-scenario campaign — which GUI surface each of the scenarios is meant
to stress, and the three headless gates that check the baselines still open and still
reproduce their metrics — see `scenarios/GUI_EXERCISE_INDEX.md`.

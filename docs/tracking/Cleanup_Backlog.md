**Usage**: any stage/task that uncovers a latent issue orthogonal to its scope appends an entry here. Entries carry enough context (file paths, commands, symptoms) to be picked up cold. Closed entries move to the "Resolved" section at the bottom with the PR or commit that fixed them.

**Not for**: items inside the current feature's scope (those go in the feature plan), scenario-specific gaps (those go in the scenario's `gaps.md`), or operational/runtime gaps already tracked in `docs/tracking/gaps.md`.

### CU-166 — Out-of-calibration NIIRS is re-announced every evaluate via two warning channels instead of being a once-read result status; no metric-applicability gate

**Discovered**: GUI-exercise campaign, 2026-07-18 — a scenario sweep in the scripting console floods with `GSD = 430 inch … outside the GIQE-5 calibration range` / `SNR = 526 … outside the GIQE-5 calibration range` on every evaluate.
**Status**: NARROWED 2026-07-18 (commit `9ae5daa`) — the warning-spam half is fixed (approach 1). The `giqe.py` `logger.warning` and the `stage.py` `warnings.warn` are removed; the out-of-calibration condition is now carried as structured status only (`GIQEResult.extrapolated` / `.warnings` / the `niirs_extrapolated` metric), with regression tests asserting zero warnings emitted. Docs `RADIANT_Metrics.md` §"Calibration range" + CHANGELOG in lock-step. **Remaining (Open)**: approach 2 (up-front metric-applicability gating — `PerformanceStage` returns NIIRS N/A via ADR-B `failure_reason` when clearly out of range), approach 3 (the MWIR→"GIQE-5"-vs-IIRS routing/label question — the secondary finding below), and approach 4 (the broader chain warning-site audit against the zero-warnings bar: saturation, `Q`-oversampling, etc.). **Update 2026-07-18 (Gap 96 landed)**: the metric-selection machinery this was gated on now exists — `performance.metrics.*` group flags + the dependency-closure gating in `PerformanceStage.run` (`radiant/performance/metric_selection.py`). Approach 2 becomes the *applicability-driven default* for those flags (turn a group's default off when the engine judges it N/A), building on the toggle rather than a parallel mechanism; approach 4 also absorbs CU-167 (three GUI warning tests stale after this CU's warning removal).
**File**: `src/radiant/performance/stage.py:762-791` (`PerformanceStage.run` computes every `_compute_*` unconditionally — no applicability gate) [remaining]. Fixed: `giqe.py` calibration check (`logger.warning` dropped), `stage.py` `_compute_niirs_metric` (`warnings.warn` dropped).
**Symptom**: the "outside GIQE-5 calibration range" condition is already carried as structured data three ways — `GIQEResult.extrapolated` (bool), `GIQEResult.warnings` (tuple of messages), and the `niirs_extrapolated` metric — yet it is *also* emitted, on **every** evaluate, as (a) one `logger.warning` per failing check in `giqe.py` and (b) a `warnings.warn` in `stage.py`. The message embeds the live SNR/GSD, so Python's dedup can't collapse repeats; an N-point sweep prints it ~2N times. A caller cannot silence the `giqe.py` channel with `warnings.catch_warnings` because it is a logging record, not a Python warning. Secondary finding to verify: scenario 1.1 is MWIR (band center 4.25 µm → `_classify_band` returns `"mwir"`, which `compute_niirs` routes to **IIRS**), yet the emitted warnings cite **"GIQE-5"** ranges — so either `compute_iirs` reuses/mislabels GIQE-5's calibration check or the MWIR case is misrouting to `compute_giqe5`; an MWIR result should not be judged against GIQE-5's vis/NIR envelope at all.
**Why it still matters**: a persistent property of the *configuration* ("this system is outside the GIQE-5 envelope") is being signalled as a per-evaluate event, which floods any consumer that runs the chain in a loop (sweeps, Monte Carlo, the GUI console/Messages pane) and buries the actual results. The information is redundant with fields already on the result. The deeper gap is that `PerformanceStage` has no notion of metric *applicability*: it computes NIIRS for every system and flags extrapolation after the fact, rather than deciding up front whether the metric is valid for this configuration (ADR-B already provides result-typed metric failures with `failure_reason` for exactly this).

**Guiding principle (acceptance target, owner-stated 2026-07-18)**: *a valid, nominally-operating physical scenario should evaluate with **zero** warnings.* A warning must mean the configuration is wrong or its results are untrustworthy (e.g. full-well saturation clipping the signal), not that a metric falls outside its own calibration band — metric applicability and confidence are structured **status**, never warnings. When valid scenarios emit warnings, users are trained to ignore the channel, so the actionable ones get missed (the same cry-wolf failure mode Rule 21 guards against). This bar generalises beyond NIIRS: every chain warning site should be audited against it and reclassified as (a) genuinely actionable warning, or (b) informational status carried on the result. NIIRS/GIQE is the exemplar; the audit is part of this CU's scope.
**Suggested fix**: **TBD** — candidate approaches, decision pending owner: (1) minimal — drop the per-evaluate `logger.warning`/`warnings.warn`, rely on the existing `extrapolated`/`niirs_extrapolated` fields, and have consumers render the caveat once (dimmed badge / one Messages line); (2) fuller — add metric-applicability gating so `PerformanceStage` returns NIIRS as N/A (`failure_reason="outside GIQE-5 calibration envelope"`) when clearly out of range, with an opt-in for callers who want the extrapolated value; (3) also resolve the MWIR→"GIQE-5" label/routing question so IIRS scenarios stop citing the GIQE-5 envelope; (4) audit the remaining chain warning sites (saturation, `Q`-oversampling notices, etc.) against the zero-warnings-for-valid-scenarios bar and reclassify each as actionable-warning vs result-status. Acceptance test: the shipped example/scenario baselines evaluate warning-free. Metric-layer + ADR-B contract change ⇒ Rule 20 doc updates (`RADIANT_Metrics.md`) and a Rule 29 CHANGELOG entry when landed. Effort M–L; category C.

### CU-164 — 20 scenario runners execute their full analysis at import (no `__main__` guard) — importing them re-runs sweeps and overwrites committed figures

**Discovered**: GUI-exercise baseline derivation, 2026-07-18 — deriving a GUI-loadable YAML per scenario imports each `run_*.py` to reach its config factory; 20 of 37 runners ran their whole analysis on import.
**Status**: Open — worked around in the GUI tooling (`scenarios/tools/_runner_import.py` imports inside a hermetic context that no-ops `savefig`/`Workbook.save`/`to_excel` and halts the module at its first `Sensor.evaluate`); the runners themselves are unchanged.
**File**: unguarded runners — `scenarios/{01/1.3,1.4}`, `02/{2.1,2.2,2.3,2.5}`, `03/{3.2,3.4}`, `04/{4.1,4.3}`, `05/{5.1,5.2,5.3,5.4}`, `06/6.3`, `07/{7.1,7.2,7.3,7.4,7.5}` `scripts/run_*.py` (each lacks `if __name__ == "__main__": main()`).
**Symptom**: `import`-ing any of these modules (as any tooling that wants the config factory must) runs the sweep, prints the full report, and calls `fig.savefig(...)` into the committed `outputs/*.png` — a plain import mutates git-tracked artifacts (observed: ~30 figures modified before the hermetic guard was added) and, on a headless backend, one runner (`1.4`) crashed in `plt.show()`.
**Why it still matters**: Rule 26 (generated artifacts are regenerable, committed only with cause) and reproducibility both assume a figure changes only when its generator is *run*, not merely *imported*. Module-scope analysis also blocks any reuse of a runner's factory (tests, tooling, cross-scenario config sharing) without side effects.
**Suggested fix**: (b) stand-alone task — wrap each unguarded runner's module-scope analysis in a `def main() -> None:` + `if __name__ == "__main__": main()`, leaving the top-level factory/constants importable. Mechanical, behavior-preserving (the committed figures are byte-identical when `main()` runs); regenerate figures once to confirm. Effort M (20 files); category A. Removes the need for the `_StopModuleExec` halt in `_runner_import.py`.

### CU-165 — A single chain `evaluate()` takes ~123 s for a heavily-oversampled (Q≈8, f/20) config

**Discovered**: GUI-exercise campaign, 2026-07-18 — scenario 6.4's baseline (`synthetic_scene`, the runner's own `APERTURE_M=0.05, FOCAL_M=1.0` ⇒ f/20, 25 µm LWIR pixels, 500 wavelength points) took **123 s** for one `evaluate()` in the real GUI (`open + first-eval = 0.4 s`, the subsequent full evaluate = 123.4 s), making the GUI freeze on Run and the scenario's console sweep (8 evaluations) impractical (~15 min).
**Status**: Open — measured, reproducible; the config is faithful to the validated runner (`scenarios/06_dr_chen_researcher/6.4_synthetic_scene_generation/scripts/run_synthetic_scene.py`), so this is engine cost, not a baseline error.
**File**: PSF/MTF path grid sizing — `src/radiant/optics/` (pupil/PSF grid + per-wavelength FFT); reproduce with `Sensor.from_yaml("scenarios/06_dr_chen_researcher/6.4_synthetic_scene_generation/inputs/6.4_synthetic_scene_generation.gui.yaml").evaluate()`.
**Symptom**: at Q ≈ 8 (detector Nyquist ≫ diffraction cutoff — the chain already warns "detector oversamples the optics") the PSF-path grid must be large to avoid aliasing, and it is recomputed per wavelength across the 500-point axis, so wall-clock scales into minutes for an otherwise small single-pixel chain.
**Why it still matters**: a 2-minute evaluate makes the GUI look hung for any legitimately oversampled design (long focal length / small aperture is common for LWIR), and no progress/cancel affordance covers it here; trade studies that sweep such a config become hours-long. The result is correct — only the cost is the problem.
**Suggested fix**: (b) stand-alone task — profile the PSF-path grid sizing at high Q; cap or decouple the pupil-grid size from Q (the *sampled* PSF only needs the detector-pitch resolution), and/or reuse the per-wavelength pupil grid instead of re-FFTing 500× when only the wavelength scale changes. Category C (touches the PSF numerics — needs a consistency-check regression, Rule 4). Effort M–L. Interim: the GUI's existing progress/cancel plumbing should wrap `evaluate()` so a slow run is cancellable rather than a freeze.

### CU-019 — `ChainResult.to_provenance_record()` referenced in docs but no implementation existed — RESOLVED 2026-04-25 (commit `70e512d`)

**Discovered**: 2026-04-25 audit, tracked as CU-NEW-04 in `audit_2026/Reconciliation_Tasks.md`. `RADIANT_Master_Architecture.md` §C13, `RADIANT_Signal_Chain_Architecture.md` §7 (`ChainResult` interface listing), and `RADIANT_Parameter_System.md` provenance-audit section all promised that every `ChainResult` exposes a complete provenance record (run ID, RADIANT version, git commit, Python version, dependency versions, resolved parameter set, input file hashes, active models). The actual `radiant.io.results.ChainResult` had no `to_provenance_record()` method — and even if it had, none of the supporting plumbing existed: `ChainState` had no `run_id` field, no helper for `git_commit` / `dependency_versions` lived anywhere in `core/`, `ParameterSet` did not track which YAML files had been loaded, and `RadiantSession.run` did not pass `params` through to the result. **File**: `src/radiant/core/provenance.py` (new); modifications to `src/radiant/core/chain.py`, `src/radiant/core/parameters.py`, `src/radiant/io/config.py`, `src/radiant/io/results.py`, `src/radiant/api/session.py`.
**Resolution**: Built the §C13 contract end-to-end in five layers.
